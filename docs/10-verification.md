# Verification

Every requirement in this documentation is checked. This page lists each requirement id with how it is checked and its status. It describes the **hosted version**, which is being built in three steps (see [Roadmap](#/docs/09-roadmap)); this pass is step 1, 26 November 2026.

## How verification works

- **Unit tests** (Vitest, `npm test`) cover the pure logic shared by the browser and the server (`src/domain`: score maths, the suggested score, plans, fingerprints, validation of imported files, the bank rules, CSV), the browser's helpers, and this page (`src/docs/traceability.test.ts`).
- **Server tests** (Vitest, `npm run test:server`) run the real server against a real PostgreSQL: every test file gets its own database, cloned from one migrated template. They cover migrations, sign-in with a stand-in Google and with the real OpenID library against a local provider, sessions, permissions for every route and role, the Users API, the question bank API, imports and the command-line scripts, live updates across two server instances, security headers, errors, limits, logs and configuration.
- **End-to-end tests** (Playwright, `npm run e2e`) build the app, create a fresh database with the same commands a deployment uses (`db:migrate`, `db:seed`), start the production server with development sign-in (`AUTH-6`) and drive the real UI in Chromium. Every end-to-end test also fails if the app logs a console error (a Content Security Policy violation included) or makes a request to another origin.
- **Seed validation** (`npm run validate:seed`) checks the bundled track files against the schema and the `BANK-3` checks.
- **Manual checks** cover what automation cannot judge here: a real Google sign-in, building the container image and deploying on Google Cloud (no Docker or Google Cloud where this was written; see `docs/deploy/README.md`), and keyboard and screen-reader passes. They are named in the table.

CI runs all of these on every push and pull request, plus a container build. A unit test (`src/docs/traceability.test.ts`) keeps this page honest: it fails if a requirement id in the other pages has no row here, if a row names an id that no longer exists, or if a row cites a test file that is missing or has no test mentioning that id.

Status means: **Automated**, checked by the cited tests; **Partial**, the automated tests check part of it and the rest is a manual check; **Manual**, checked by a person only; **Not built yet (step 2 or 3)**, specified but not built in the hosted version yet (allowed only for the ids listed in `src/docs/traceability.test.ts`, which are removed from that list as they are built). The local app built and checked all of those; its tests are kept in `e2e-local/` and `src/db-local/` so each can be ported with its screen.

In the tables, `src/...test.ts` files are unit tests, `server/...test.ts` files are server tests against PostgreSQL and `e2e/...spec.ts` files are end-to-end tests. The quoted words identify the test title.

## Notes from the step 1 verification pass

Places where the documentation could be read more than one way, and what the hosted version does. They are proposals for the owners of the documentation.

- **Importing over changes made in the app (`DB-2`, `BANK-11`).** A question whose version in the database is higher than in the file was edited in the app after the file was made; the import leaves it alone and reports it as "kept (newer in the database)", so running `npm run db:seed` or an old file again never undoes work done in the app. A changed question gets version max(database + 1, file). Categories, retired status and the track name follow the file. Questions in the database but not in the file are left alone. CSV files have no question ids, so their rows are matched to the track's questions by question text. Proposed addition to `DB-2`: "A question changed in the app since the file was made is left as it is and reported."
- **Who may upload files in the app (`DB-3`, `USER-2`).** Uploading is for administrators, as `DB-3` says; organisers edit the bank and export it but do not upload files.
- **"Not yet exported" (`BANK-14`).** Kept per track: it starts with the first change made in the app (not with imports from files) and clears when the track is exported as a track file.
- **Hiding other people's scores (`LIVE-3`, `FLOW-27`).** The setting's name, "Hide other people's scores until they have submitted", reads as "until each of them has submitted", which would let you see a submitted colleague's scores before you score; the local app's rule (and the point of independent scoring) is "until you have submitted yours". Proposed wording: "Hide other people's scores until you have submitted yours". Step 2 decides.
