# Verification

Every requirement in this documentation is checked. This page lists each requirement id with how it is checked and the result of the last verification pass (24 November 2026).

## How verification works

- **Unit tests** (Vitest, `npm test`) cover the pure logic and the local database: score maths, the suggested score, plan building, fingerprints, validation of imported files, timers, exports, and every repository function (using an in-memory IndexedDB).
- **End-to-end tests** (Playwright, `npm run e2e`) build the app, serve the production build with the real local helper (`server/`, as `npm start` does) and drive it through the real UI in Chromium. The helper runs a deterministic stand-in for the Claude Code command-line tool (`server/test/fake-claude.mjs`), so the AI second opinion is exercised end to end with no network and no real model call; two more helper instances answer with output that does not fit and slowly. Separate browser contexts play separate panelists. Every end-to-end test also fails if the app logs a console error or makes a request to another origin.
- **Helper tests** (Node test runner, `npm run test:server`) cover the local AI helper: localhost only, origin and header checks, size limits, no tools, the fixed prompt, output checks and logging without content.
- **Seed validation** (`npm run validate:seed`) checks the question bank files against the schema and the `BANK-3` checks.
- **Manual checks** cover what automation cannot judge. They are named in the table with what to do.

CI runs all of these on every push and pull request. A unit test (`src/docs/traceability.test.ts`) keeps this page honest: it fails if a requirement id in pages 01-09, 11 or 12 has no row here, if a row names an id that no longer exists, or if a row cites a test file that is missing or has no test mentioning that id.

Status means: **Automated**, checked by the cited tests; **Partial**, the automated tests check part of it and the rest is a manual check; **Manual**, checked by a person only; **Not built yet**, specified but not built (allowed only for the ids listed in `src/docs/traceability.test.ts`, which are removed from that list as they are built).

In the tables, `src/...test.ts` files are unit tests and `e2e/...spec.ts` files are end-to-end tests. The quoted words identify the test title.

## Notes from the verification pass

These are places where the documentation could be read more than one way, and how the app behaves. They are proposals for the owners of the documentation; the app follows the reading given.

- **New interview and the ready screen (`FLOW-7`, `FLOW-8`, `FLOW-33`, `PRIV-4`, `TR-4`).** "Continue" pins the plan and creates the interview with no consent time (`consentAt` is empty); the ready screen stores it when the interviewer confirms and presses Start, and the repository refuses to start an interview without it. The consent confirmation is audited ("Consent confirmed"), as is discarding an interview before it starts ("Interview discarded before it started"); proposed addition to `AUD-2`: "…consent confirmed; an interview discarded before it started". The "recorded or transcribed" choice made at setup is kept on the interview (`candidate.recordingNotice`) until the ready screen confirms it. Discarding returns the plan to a draft with the candidate details filled in; when other interviews use the same plan it stays pinned and a new draft that reuses it is made instead. "New interview" picks up the newest draft that has nothing typed for a candidate, so opening it twice does not leave empty drafts behind. Proposed wording: `FLOW-9` "…reused for another candidate (\"New interview with these questions\", or \"Use the same questions as…\" on the New interview screen)…" (the current quoted label uses the word "plan", which `UX-8` keeps off screens); `PANEL-1` "Interviewers are named when the interview is set up (New interview › More options)…"; `A11Y-2` "…(the ready screen)".

- **Live interview and finishing (`UX-4`, `UX-5`, `UX-6`, `KEY-1`, `RUB-1`, `FLOW-23`).** "Visible without scrolling" is measured at 1280 × 800 between the two bars: the top bar (candidate, role, interviewers, overall time, the question strip, Pause, "More", Finish) stays at the top of the window from 1024 px up, and the bottom bar (Previous, Flag, Skip, the question's time, the four score buttons, Next) is fixed to the bottom at every width. While an interview is running or paused, the header has the app name and "Exit to dashboard" only, and help links open the documentation in a new tab, so no link on the screen leaves the interview; the ready screen and a submitted interview keep the full navigation. Each score button shows its number and label; its description appears while it is hovered or focused, is its accessible description, and all four are listed under "Rubric" (proposed wording for `RUB-1`: "…shown wherever a score is chosen: each level's label, with its description on hover, focus or in the rubric list"). Shortcut hints are in tooltips, the "More" menu and the shortcuts dialog (which also explains the question strip) instead of on every control; the keys are unchanged. "Skip the rest with one reason" skips, in one transaction, every question that is neither scored nor skipped; questions skipped earlier keep their own reason, and each skip can be undone on its question (or all of them at once from the finish step) until the interview is submitted. Screens say "submitted" and "read-only" rather than "locked"; the record is still locked as `FLOW-23` says (proposed wording: "Finishing **submits** the record; it is then read-only, and any change requires a reason…").
- **Words on screens (`UX-8`, `FLOW-1`, `FLOW-9`, `FLOW-26`).** The plan fingerprint is shown as the "comparison code", a plan as a "question set", a session file as an "interview file for the debrief", and the planned state as "Ready to start". Proposed wording: `FLOW-1` "…with their state (ready to start, in progress, paused, submitted)"; `FLOW-9` "…a *plan fingerprint* (shown on screens as the comparison code)…"; `FLOW-26` "A submitted interview can be exported as a file for the debrief (JSON)…".
- **Retention date (`PRIV-5`).** The app reads "sessions past their retention date are purged" as: the retention date is the last day a session is kept; it is purged when the app is opened on any later day. Proposed wording: "The retention date is the last day a session is kept. The first time the app opens after that day, the session is purged…"
- **Audit log and deletion (`AUD-1`, `PRIV-5`, `PRIV-6`).** An "edited after submission" entry stores the values before and after, which can include note or rationale text about the candidate. When a candidate's session is deleted (deletion request or retention purge), the app keeps the entry (time, actor, action, entity, entity id) but replaces its before/after values with the list of fields that changed, and its reason with "[redacted]". Erase-all clears the whole log and records one entry. Proposed wording for `AUD-1`: "The app offers no way to edit or delete individual entries. When a session is deleted by a deletion request or the retention purge, candidate text in its entries (before and after values and reasons) is redacted; the entries themselves are kept."
- **Draft candidate details (`RES-1`, `FLOW-7`).** Candidate details typed on the Setup screen before the plan is locked are saved in the local database, so closing the tab loses nothing. They are removed when the plan is locked (they move to the session) or deleted, by a deletion request for that candidate key, by erase-all, and by the retention purge once their retention date has passed. An access request includes them. Proposed addition to `PRIV-6`: "…including candidate details typed on plans that were never locked."
- **Question versions (`FLOW-9`, `BANK-11`).** Edits made in the app raise a question's version as `BANK-11` says. A hand edit of a seed file does not: whoever edits by hand raises the `version` when the meaning changes (README, "Changing the question bank").
- **Category renames (`BANK-12`).** Category ids are `<trackId>-<slug of the name>` when a category is created. A rename keeps the id, so questions, plans and fingerprints that refer to it are unaffected; the id may then no longer match the name.
- **Full-sentence key points and red flags (`BANK-15`, `UX-4`, `FLOW-12`, `RUB-5`), 24 November 2026.** The bundled bank (track version `2026.11.1`, 207 questions) has five key points and four red flags per question, 12 to 30 words each. The app emphasises a leading label on key points and red flags alike, in the live interview and in the read-only lists (question detail, the ready-screen peek, a submitted interview, the scorecard's red flags and the AI comparison tables), but only when the text before the first colon is short (up to six words and 48 characters) and looks like a label: no dots ("e.g.", code such as `azure.workload.identity/use`), quotes, brackets after a word, or a list introduction such as "such as:", and the colon must be followed by a space (so URLs, times like 2:30 and "Top 10:2025" are left plain); 637 of the 1,863 bundled items get a label, 21 items with a colon are left plain. To keep `UX-4` with sentences, the checklist card is as wide as the question column, stays in view, and is never taller than the room between the bars: when a question's lists do not all fit it scrolls inside itself, with a cue at its bottom edge ("Red flags below") that scrolls to them, and the page does not scroll.
